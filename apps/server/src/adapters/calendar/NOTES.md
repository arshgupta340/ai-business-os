# Calendar adapter: integration notes

* Wiring. Build the client with `calendar({ version: 'v3', auth })` from `@googleapis/calendar`, with a service account JWT holding the scopes `calendar.events` and `calendar.freebusy` (free/busy does not accept `calendar.events`). A test checks at compile time that the real SDK client satisfies `GoogleCalendarClient`. Inject the authenticated client only into approved execution and operator cleanup paths.
* The executor checks owner approval and holds the per-calendar local slot lock (booking in `RECHECKING_SLOT`, SPEC 2.9) before it calls `createEvent`. This adapter has no database or approval engine dependency.
* `AvailabilityQuery` carries `serviceId` because `AvailabilitySlot` requires it, and an optional `maxSlots` (1 to 5). Hours are the per-weekday `hours` facts, keys `mon` to `sun`. Hours that cross midnight are rejected as `VALIDATION_FAILED`.
* Buffer. The buffer is added after the service only: it must be free of busy blocks but may run past closing. The inserted event covers the service only.
* Conflict alternatives. Pass `alternativesQuery` (the booking's date, service, time zone, hours, buffer and minimum notice, loaded fresh from facts) to `createEvent`. Without it, or if the alternatives lookup fails, the result is still `SLOT_CONFLICT`, with an empty alternatives list. The adapter never invents hours or a service.
* Event id. Pass the step's `idempotencyKey` (CONTRACTS 5) as the Google event id. If it is absent the adapter uses sha256(bookingId). Both are 64 lowercase hex characters, which fit Google's base32hex id rule.
* Private property. Key `bookingId`, value the first 44 hex characters of sha256(bookingId), always exactly 44 characters. The full booking id goes in the description.
* Retry lookup. Before any free/busy read or insert, the adapter looks for the event by the private property, then by the event id. An insert error, timeout or 409 is an unknown outcome: the same lookup decides, and the adapter never inserts twice in one call. If the lookup finds nothing, the result is `INTEGRATION_UNAVAILABLE` (retryable); retry with the same booking id and key. The executor's NEEDS_REVIEW policy for unknown results stays outside this adapter.
* Timeouts. Each provider call has a timeout (default 8000 ms, `timeoutMs` in deps). A timed-out call may still complete at Google; the deterministic event id makes a later insert fail with 409, which the lookup resolves.
* Unverified: after `deleteEventForBooking`, Google may keep the deleted event id, so inserting the same booking again could return 409 with no live event, giving `INTEGRATION_UNAVAILABLE` on every retry. Use a new booking id after a reset. Not tested against Google.
* No real Google API was called. All verification uses injected fakes.
