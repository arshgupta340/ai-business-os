# B-15 notes: things outside apps/server/src/voice and tools/real

1. **Register the plugin (app.ts, not edited).** `await app.register(voicePlugin, { publicServerUrl, liveAgent, facts, calls, events, decisions, toolsetFactory, twilioValidator: createTwilioRequestValidator(TWILIO_AUTH_TOKEN), openaiSocketFactory: createWsOpenAISocketFactory({ apiKey: OPENAI_API_KEY }), messageChannel, twilioBusinessId, redactSecrets: [OPENAI_API_KEY, TWILIO_AUTH_TOKEN] })`. The toolset factory should be `(ctx) => { const ts = createRealToolset({ ...ports, businessId: ctx.businessId, capabilities: ctx.capabilities, factsSnapshot: ctx.facts, messageChannel }); return { handler: ts.handler, dispose: ts.dispose }; }`. The plugin registers `@fastify/formbody` and `@fastify/websocket` itself unless the app already has them.
2. **env.ts (not edited)** needs `TWILIO_AUTH_TOKEN`, `OPENAI_API_KEY`, `MESSAGE_CHANNEL` and a required `PUBLIC_SERVER_URL`.
3. **Capability rule.** `AgentSpec.capabilities` holds the tools plus the executor bundle, so a literal "refuse any write capability" would refuse every real spec. `checkSessionCapabilities` refuses unknown ids and any write or external_message capability outside the bundle of a propose capability the spec holds.
4. **Stream credentials.** One per CallSid, kept in memory: a repeated webhook gets the same pending token; after the stream claims it, or once it expires or the call ends, retries get 409. After a restart, `CallsPort.findByProviderCallId` refuses a stored call. Two simultaneous deliveries on two server processes rely on the unique `provider_call_id`: `startCall` must throw on a duplicate (the caller then hears the setup-failed message and no second credential exists).
5. **Read-back and consent (finding 11), remaining exposure.** The contract fixes seven tools, so the read-back is enforced inside the proposal tools. A consented recipient must be presented in one proposal call (which returns `missingFields: ["contact.messageRecipient.readBack"]` and stores nothing) and confirmed by a second call with the same number at least 3 seconds later. `consentAt` is set by the server. Changing the number restarts it, and the state is per call. The server never hears the caller (no transcript is read), so it cannot prove the caller said yes, or that the number is not the caller ID the model assumed. A model that waits and repeats the call can still pass. The owner approval of the exact recipient is the remaining check.
6. **Late proposals (finding 5), remaining exposure.** A tool that misses its deadline is abandoned, and the toolset refuses to call the proposal port afterwards. A proposal port call that is already running when the deadline passes can still finish, so `ProposalPort` must check that the call is still `IN_PROGRESS` in its transaction.
7. **Unverified vendor behavior** (in addition to the Twilio leg, which has never run on a real call): the injected server status item (`conversation.item.create` with a `message` item, role `system`, `input_text`), `conversation.item.truncate` with `audio_end_ms: 0` for audio not yet heard, and that closing the Media Stream ends the call after `<Connect>`. The spike proved only the session shape, audio deltas, function calls and `function_call_output`.
8. **docs/FLOWS.md B12 is out of date.** A caller who declines messages can finish an order (SPEC 2.9 ruling): no recipient, channel `qr_only`, link shown at the counter.
9. **Not built here:** `/webhooks/twilio/status`. The relay re-reads the call status every 15 seconds instead, so a call ended elsewhere stops it.
10. **Ports for other workers:** `OrderStatusPort.read` returns null for another business or another call; `AvailabilityPort.freeSlots` computes from the pinned service and hours it is given; `VoiceEventsPort` writes `webhook.rejected` and `guardrail.refused` with the payloads given.
